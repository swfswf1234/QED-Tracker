# 测试架构与门禁

状态：Current
确认状态：已确认
最后更新：2026-08-31
治理对象：测试职责与隔离边界、门禁组成、治理契约测试的守护面清单、契约头、编写约定与新增流程
依据：QED-Engine 根仓库 `docs/standards/testing.md`「三项目复用（范本）」适配（[ADR 0004](../adr/0004-standards-governance-alignment.md)）
关联测试：`tests/test_documentation.py`

## 目的与边界

本标准定义 QED-Tracker `tests/` 如何保护已采纳的确定性契约（来源协议、下载校验、目录匹配、
服务行为与文档治理规则），并规定「治理契约测试」的编写规范：把标准正文中的强制规则翻译为
可执行断言，防止规则漂移。外部来源与模型在线可用性不由测试回答，由人工检查并记录。

边界：

- 本标准管「全部测试的架构与门禁」与「治理契约测试的守护面清单、契约头、编写约定与新增流程」，
  统一维护于此，不拆分独立标准。
- 可复制命令只在[开发指南](../guides/development.md)维护，本标准不复制命令。
- 标准/ADR 等文档的元数据规则在其对应标准正文，本标准不重复（一个事实只设一个维护位置）。
- 守护面清单的唯一维护位置在本标准；`tests/test_documentation.py` 从其提取清单语义源。

## 强制规则

### 测试分层

当前测试平铺于 `tests/`（不强制分子目录）：

| 层 | 职责 | 代表 |
| --- | --- | --- |
| 行为测试 | 配置解析、目录匹配、来源归一化、下载校验、资源登记、服务 API 与 CLI 行为 | `tests/test_config_catalog_matching.py`、`tests/test_services.py`、`tests/test_api.py`、`tests/test_cli_architecture.py` 等 |
| 治理契约测试 | 文档治理、映射与任务治理（只解析仓库内文档与源码） | `tests/test_documentation.py` |
| 真实环境冒烟 | 默认 skip 的 MySQL 三表冒烟，仅人工触发 | `tests/test_db_three_table_smoke.py` |

后续新增集成层（HTTP 适配器、系统级联调）时，参照根仓库与 Axiom-Flow 分层模式建立
`integration/`、`system/`、`smoke/` 并登记 ADR。

### 隔离铁律

- 默认测试不得访问公网；来源协议变化使用固定 fixture 覆盖，真实连通性由人工检查并记录。
- 自动测试不得要求 API key、不得调用外部模型服务、不得写入真实数据根或运行数据库。
- 真实 MySQL 冒烟必须默认 skip，由人工显式触发。
- 测试不依赖工作目录之外的绝对路径；相对仓库根的路径通过 `Path(__file__)` 推导。
- TLS 校验默认开启的约束不得被测试绕过（测试内关闭 TLS 只允许出现在显式声明降级行为的
  用例中）。

### 门禁组成

- 本地门禁为唯一门禁（不依赖远端 CI）；wheel 构建不作为门禁。
- 提交前完整门禁以[开发指南](../guides/development.md)「验证门禁」节为准：全量 pytest、
  ruff 检查、`qed-tracker --version` 与 catalog 冒烟，全部通过方可声称完成。
- 文档治理类变更必须运行 `tests/test_documentation.py` 并全绿。
- 覆盖率只作盲区证据，不设 `fail-under`；覆盖率不能替代关键状态转换、错误路径和回滚场景测试。

### 治理契约

#### 守护面清单

| 治理面 | 守护内容 | 契约测试 |
| --- | --- | --- |
| architecture | 架构文档入口集合、元数据、链接完整性 | `tests/test_documentation.py` |
| design | 设计文档元数据、DesignRef 引用、代码/测试路径引用 | `tests/test_documentation.py` |
| standards | 标准元数据、Legacy 词禁令、文档时效性 | `tests/test_documentation.py` |
| guides | 操作入口不链历史、CLI 命令与 parser 一致 | `tests/test_documentation.py` |
| trackers | tracker ID 唯一性、活跃计划关联、无重复关闭 | `tests/test_documentation.py` |

- 表格固定 3 列（治理面 / 守护内容 / 契约测试），首行为表头。
- 新增治理面或既有治理面新增守护对象时，先更新本清单与契约测试 docstring，再改断言。

#### 契约头

每个治理契约测试的测试函数以 docstring 声明完整契约头（六字段）：

```
"""
守护：<一句话验证目标>

模块职责：<验证什么保持一致>
设计关联（DesignRef）：docs/standards/<对应标准>.md「<章节>」
实现状态：Implemented
被测代码：<守护对象路径，多个用顿号分隔>
守护面：<守护面清单中的治理面>
失效后果：<测试失败说明哪条治理规则被违反>
"""
```

- DesignRef 指向守护的核心标准；同一函数被多个标准关联时可声明多行（第一行为核心标准）。
- 实现状态取值与[文档治理规范](doc-governance.md)「元数据」一致；历史守护场景进入
  `history/` 后不再守护。

#### 编写约定（自包含与零依赖）

- 只使用 Python 标准库与被测公共入口（如 `build_parser`），不引入测试专用第三方依赖。
- 文件自包含：不依赖共享 helper 目录；辅助函数允许在各文件内重复编写。
- 仓库相对路径一律通过 `ROOT = Path(__file__).resolve().parents[1]` 推导，不依赖工作目录。
- 只解析仓库内文档与源码，不发网络请求、不加载生产服务（与「隔离铁律」一致）。
- 断言失败消息指明违规对象与路径，便于定位。
- 白名单断言（入口集合）必须同时校验「当前集合 == 白名单」与「历史集合并集」，防止文档
  未登记混入或历史文档回流当前层。

#### 新增/修改治理契约测试的流程

1. 治理规则变化：按 [ADR 治理规范](adr-governance.md) 判断是否需新增 ADR，修改对应标准正文。
2. 确定守护对象：明确新规则守护哪个治理面、哪个文档/代码对象（先列清单，再写断言）。
3. 编写契约测试（契约头 + 断言新规则），运行确认红（规则尚未生效或对象未满足）。
4. 修改标准正文或文档，运行契约测试确认绿（先红后绿）。
5. 运行全量 pytest 确认新旧守护全绿。
6. 同步登记：[规范索引](index.md)的「自动门禁」列、相关标准的「关联测试」字段、
   [code-map](../architecture/code-map.md) 对应行。
7. 涉及新治理面时更新守护面清单。

## 执行与门禁

1. 新测试跟随被测模块登记：行为测试在 code-map「关联测试」列登记，治理契约测试在守护面
   清单与本标准登记。
2. 可复现缺陷先补回归测试再修复；外部质量失败进入 tracker 或人工检查记录，不写成不稳定测试。
3. 新增或修改文档治理规则时，同步更新 `tests/test_documentation.py` 并全量运行。
4. 契约测试属于 `tests/` 门禁范围，全量门禁必须全绿。

## 变更与取代

- 改变隔离铁律、门禁组成、守护面清单结构（列数/列名）、契约头字段、编写约定禁令或新增
  流程的实质规则时必须先新增 ADR。
- 目录内普通测试增删、命令勘误、措辞勘误与链接修复属于实现同步，可直接修改。
